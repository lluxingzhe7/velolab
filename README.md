# BikeFit · 骑行姿态拟合

把 MyVeloFit、Posely、PedalPro 三款商业 fitting 工具的核心能力，用零依赖的纯前端实现成一套自用工作台：
**演示模拟 → 摄像头视频采样 → 单张照片标定 → 角度报告 → 毫米级调整 → 疼痛定位 → 历史对比 → 打印报告**。

## 一、逆向对照表

| 能力 | MyVeloFit | Posely | PedalPro | 本项目实现 |
| --- | --- | --- | --- | --- |
| 测量方式 | 上传 30–60s 视频 | 手机侧拍 15s + 端上 MediaPipe | 单张照片 + AI 关节点 | 三者都有：演示合成骨架 / 摄像头 MediaPipe / 单张照片手点关节 |
| 角度指标 | 20+ 项 | 膝 33°、髋 100°、背 52° 等 | 分部位角度 | 膝（下/上死点）、髋（下/上死点）、躯干、肩、肘、足 |
| 目标区间 | 按车型/柔韧度 | 按车型 | 按车型 + 舒适/均衡/激进 | `TARGETS` 按车型 × 姿态 × 柔韧度生成 |
| 调整建议 | 分级建议 | 规则引擎给 mm 动作 | 分部位建议 | `recommend()` 给毫米级动作 + 预期角度 + 置信度 |
| 疼痛诊断 | — | Something hurts? Tap where | 分部位建议 | 「疼痛」页：9 个身体位置 → 原因 + 动作 |
| 历史与趋势 | 多次记录对比 | 趋势图 + PDF | 多份报告 | 「记录」页：快照、趋势线、与上次对比 |
| 报告导出 | PDF | PDF | 报告 | Markdown / JSON 导出 + 可打印报告（浏览器存 PDF） |
| 按身高估算初始设定 | 有 | — | — | 「按身高估算初始设定」按钮 |
| 曲柄建议 | 有 | — | — | 按身高/跨高分档给出曲柄长度 |

## 二、五种测量模式

1. **演示模式**：滑杆调节坐垫高低、躯干角偏移，模拟合成骑手，用于验证判定链路。上面 3 个数字是「真实」输入，程序并不知道你调了什么，它只从骨架几何反算。
2. **摄像头模式**：手机/相机侧拍，MediaPipe PoseLandmarker（已本地化到 `vendor/mediapipe/`，可离线）实时识别 33 个关键点，采样 7 秒后自动取多个踩踏周期的下死点/上死点平均值。
3. **照片模式**（对应 PedalPro）：载入一张侧面照，按顺序点 6 个关节（髋→膝→踝→肩→肘→腕，脚跟/脚尖可选），立刻给出膝、髋、躯干、肩、肘、足角。单张照片只评价下死点姿态，上死点相关项会显示为「—」。
4. **视频模式**（对应 MyVeloFit）：选一段侧拍视频，按 12 帧/秒抽帧识别，自动找多个踩踏周期取平均。
5. **手机联动**（手机当摄像头、电脑实时算）：见下一节。

## 二·五、手机联动（手机摄像头 → 电脑实时角度）

1. 电脑用 `node server.mjs` 启动，控制台会打印手机地址，例如 `https://192.168.3.22:4173/phone.html?code=5B1D`，以及 4 位房间码（HTTP 与 HTTPS 共用 4173，手机上只需放行这一个端口）。
2. 手机与电脑连同一 Wi-Fi，用手机浏览器打开该地址（自签证书，首次要点「继续/高级 → 继续访问」），允许摄像头权限。
3. 手机页点「开始推流」，电脑切到「手机联动」模式：画面实时回传到电脑的舞台，MediaPipe 在电脑上算膝/髋/躯干角并显示在 HUD。
4. **不用点「开始采样」**——手机联动是连续自动分析的，该模式里「开始采样/停止」会被隐藏，换成「● 自动实时分析 + 进度文字 + 保存本次记录」。
5. 摄像头必须在安全上下文（HTTPS 或 localhost）才可用，所以同一个 4173 端口会按首字节自动分流：TLS 交给 HTTPS，明文交给 HTTP。证书用 `src/cert.mjs` 纯 Node 生成（RSA2048 自签，SAN 含本机局域网 IP）。

### 自动判定什么时候出、多久刷新一次

| 阶段 | 触发条件 | 用时（实测） | 界面上看到什么 |
| --- | --- | --- | --- |
| 画面到达 | 手机开始推流 | 0.2–0.5s | 顶栏「手机画面 N fps」，舞台出现手机画面 |
| 攒够可用帧 | 检测到骑手并累计 30 帧（检测限速约 4–5 次/秒） | 6–8s | 进度条「已收 A 帧 · 可用 B 帧，约 N 秒后出第一次判定」 |
| 第一次判定 | 满 30 帧且能识别到踩踏周期 | 立即 | 结果页自动刷新 + 提示「结果页已更新，可保存为记录」 |
| 之后滚动刷新 | 每 2.4s 一次 | 每 2.4s | 进度条「最近判定 N 秒前 · 膝 X° 髋 Y°」，建议同步回手机页 |
| 保存 | 点「保存本次记录」 | 立即 | 「已保存为第 K 条记录」，记录页可对比趋势 |

识别不到骑手时（整车没入镜、逆光、纯黑宽松裤）进度条会直接说「已收 N 帧，但还没识别到骑手（整车入镜、正侧面、光线足一点）」，不会假装在算。

自检：`test/live-sim.mjs`（喂合成踩踏帧 → 结果页出现角度/建议、进度条更新、保存后记录 +1），`test/phone-ui.mjs`（手机模式工具栏变成自动分析状态）。

### 手机页的横屏、镜头、变焦、画幅

| 控件 | 作用 | 什么时候用 |
| --- | --- | --- |
| 右上「横屏」 | requestFullscreen + `screen.orientation.lock("landscape")`，同时把布局切成横屏（视频吃满、控制条压成底部浮层） | 房间窄、需要把整车横向装进画面时 |
| 镜头下拉 + ↻ | 列出 `enumerateDevices` 拿到的所有摄像头；名字带 wide / ultra / 0.5× / 广角 的排前面并标「（广角）」；↻ 重新扫描 | 手机确实暴露了多个后置镜头时 |
| 最广 / 1× | 「最广」= 镜头硬件的最小倍率（有 0.5× 时就是超广角），「1×」= 回到主摄视角 | 想一键回到最广或主视角 |
| 变焦滑杆 | 有硬件 zoom 能力就走硬件变焦（清楚）；没有就走中心裁切（标签写「数码」，会糊） | 稍微补构图，别当广角用 |
| 16:9 / 4:3 | 改 `getUserMedia` 的 height 与 aspectRatio（720p ↔ 960p） | 4:3 多出上下视野，房间矮、整车竖着装不下时用 |

**为什么很多手机看不到「广角」选项**：浏览器只能选手机暴露给网页的 `videoinput`。iPhone（Safari 与第三方浏览器内核都一样）基本只暴露 1 个摄像头；多数 Android 也只暴露 1 个逻辑摄像头。只有两种情况能拿到超广角：系统把超广角作为独立 videoinput 暴露出来，或 Camera2 逻辑多摄把 `zoom` 的 min 报到 0.5 以下。

手机页会先探测再说话，不会给一个点了没反应的下拉：

- 拿到多个镜头 → 下拉里列出名字，可疑的更宽那个会标「（广角）」；切完可以直接看画面装下多少。
- 只拿到 1 个、且 zoom 最小是 1× → 控制条下方直接写「本机浏览器只开放 1 个摄像头，拿不到 0.5× 超广角（iPhone 基本都这样，Android 也常见）」，并给三条退路。
- 数码变焦时「最广」按钮自动隐藏（它和「1×」是同一件事），滑杆拉到 1.6× 以上会提示「人离得越远越糊」。

房间小、拿不到超广角时的三条退路（按优先级）：

1. **退到最远 + 横屏 + 镜头降到车把高度**：1.8m 的整车在 2m 距离、主摄 16:9 下大约占画面 60–70%，够 MediaPipe 用。
2. **切 4:3**：上下视野多出约 1/3，头到脚更容易同时入镜（左右会窄一点，镜头要正对车身侧面）。
3. **用系统相机 App 的 0.5× 录 10–30 秒侧面视频**，传回电脑后用「视频」模式分析——这条路能用上手机原生超广角，代价是要传文件。

自检：`test/phone-cam.mjs`（无头 Edge 假摄像头：横屏类名/按钮文案/镜头下拉/变焦标签/4:3 后视频变 1280×960/开始推流），`test/zoom-check.mjs`（裁切与能力判断的纯函数，15 条断言）。

### 为什么不卡（性能架构）

卡顿的根因不是带宽，而是 **MediaPipe 推理是同步的**：一次 `detectForVideo` 在 CPU 上要 100–300ms，直接跑在主线程里画面就会一顿一顿（旧版本还会把 720p 整帧塞进模型，更慢）。现在的做法：

- **推理进 Worker**（`src/pose-worker.js`）：主线程只负责解码 + 画图，推理再慢也不影响画面刷新。Worker 不可用时自动退回主线程，并按实测耗时降频。
- **只处理最新帧**：收帧用「最新一帧」槽位覆盖，处理不过来就丢旧帧，永不排队——不会越推越卡。
- **检测限速 + 在飞帧上限**：最快 90ms 一次、同时最多 2 帧在算，避免把 CPU/GPU 灌满。
- **缩略图进模型**：送进模型的图缩到 480px 宽，关键点坐标再换算回原始像素。
- **手机端背压**：`ws.bufferedAmount` 超过 260KB 直接丢帧；编码慢就自动拉长间隔（80–180ms 自适应）；推流 640 宽 q0.58，约 25–35KB/帧。
- 实测（无头 Edge、纯 CPU 推理，1440×1000 的 PNG 连续推）：主线程单帧最大耗时 24–27ms（旧版是 8900ms），收 90 帧能画 78–80 帧。

性能探针：`test/phone-perf.sh`（模拟手机连续推帧，读 `window.__phonePerf` 的收帧/绘制/推理耗时）。

### 顶栏为什么会出现 23fps（两个手机页面在推）

手机端最快 80ms 一帧，单台手机最多约 12.5fps，所以 23fps 只可能是**同一个房间有两台手机页面在推**（手机上开了两个标签页、或者电脑上同时开着手机页）。旧版房间里的连接不会清理，刷新几次就堆出一串假连接，帧也会往死 socket 里写。现在做了三件事：

1. **连接生死透传 + 心跳**：前门 socket 关闭会连带关掉内部连接，另外每 10 秒发一次 WS ping、30 秒没有任何上行就清掉（`WS_IDLE_MS` 可调），房间计数不再只增不减。
2. **一个房间只保留最新那台手机推流**：新页面加入时，旧的收到 `{t:"superseded"}` 并自动停推，提示「已被接管」，点「开始推流」可以抢回来。
3. **被接管的连接不再转发帧**：电脑端帧率回到单源，画面不会在两支镜头之间来回跳。

自检：`test/live-multi.mjs`（接管与停转发）、`test/live-clean.mjs`（断开后计数回落）、`test/phone-supersede.mjs`（手机页真的停推流）。

## 三、面板说明

- **骑手 / 车辆**：身体数据与车设定，改完立即参与推算；数据存 localStorage。
- **结果**：实测角度（带目标区间与正常/偏高/偏低判定）、调整建议（部位 + 动作 + 依据 + 预期）、当前设定 vs 按身高估算。
- **疼痛**：点人体上的位置（可多选），按实测角度匹配原因与动作；没有测量时只给排查方向。
- **记录**：保存本次快照、趋势折线（膝/髋/躯干可选）、与上一次逐项对比、删除/清空。
- **报告**：一页式报告（骑手车辆、角度表、建议、疼痛），点「打印 / 另存 PDF」走浏览器打印。

## 四、术语与量法（界面里也有同样的说明）

**柔韧度 1–5**（坐地双腿伸直、手掌叠放缓慢前屈，看指尖到哪）：1 僵硬 = 指离脚尖 >10cm 且腰背拱起；2 偏紧 = 0–10cm；3 一般 = 指尖碰到脚尖；4 较好 = 指根碰到；5 柔韧 = 掌心贴地或胸贴大腿。档位只平移目标区间：每低一档，髋角与躯干角目标各放宽约 3°。

**坐垫高（BB→坐垫顶面）**：沿座管方向从中轴中心量到坐垫表面中心，不是垂直高度、也不是量到最高点。

**坐垫后移（BB→鼻尖）**：过中轴挂一条铅垂线，量坐垫鼻尖到这条线的水平距离，坐垫在后方为正。要知道该移多少不用先猜——看下死点膝角，以及 3 点钟时胫骨粗隆的铅垂线应落在踏轴前后 ±10mm；程序说「后移 5mm」就按坐垫夹块在导轨上的位移量移动再重测。

**坐垫→把横落差（bar drop）**：坐垫顶面与上把顶面的高度差（各量到地面的高度相减），70mm 左右舒适，120mm 以上偏竞技。

**把横 Reach / Drop**：把立前端中心到上把前缘的水平距离（常见 70–90mm）；上把顶面到下把最低点的垂直落差（常见 120–145mm）。

**把立角度**：相对水平的夹角，常见 -6°、气动 -17°，只影响报告文字，不参与角度判定。

**垫圈总高**：把立下方所有垫圈之和，公路车常见 10–40mm，铁三车常见 0–30mm。

**铁三垫面高 / 垫中心前后**：中轴到休息把垫面顶部的垂直高度（常见 600–680mm）；中轴垂线到垫面中心的水平距离，前为正（常见 400–500mm）。

**留空的规则**：不清楚就留空，程序按身高/跨高补估算值（输入框显示灰字「估算 742」，并标虚线）。只有「坐垫高」与「曲柄长」参与角度换算（曲柄用于像素标定：踝部竖直行程 ÷ 2×曲柄），其余字段只影响建议文案与报告。

**车种与车型联动**：车辆页「车种」与骑手页「车型」是同一个设定，改一边另一边跟着变——目标区间由车型决定，两边不一致会让判定和你的车对不上。铁三休息把字段只在铁三车时显示。

## 五、手机打不开联动地址

手机能上网、但打不开这个地址，**最常见的原因是 Windows 防火墙**：这台电脑的 Wi-Fi 被系统判定为「公用网络（Public）」，公用配置默认丢弃所有外部主动连进来的端口——手机发来的请求在进不了 Node 进程之前就被丢了，所以手机会显示「网站暂时无法打开」，而它自己访问互联网是完全正常的。实测依据：目标机 `Get-NetConnectionProfile` 为 `NetworkCategory = Public`，三个防火墙配置（Domain/Private/Public）都是 `Enabled`，且不存在 4173 的入站规则；同时 `arp -a` 里能看到手机（192.168.3.52）的 MAC，说明手机和你已经在同一网段、二层是通的。添加规则需要管理员权限，普通进程无法代劳，所以做了个一键脚本。

1. **双击 `开启手机访问.bat`**，在 Windows「用户账户控制」窗口点【是】。脚本会执行：
   `netsh advfirewall firewall add rule name="VeloLab-4173" dir=in action=allow protocol=TCP localport=4173`
   脚本最后会回显这条规则，能看到 `VeloLab-4173` 就说明生效了（只需做一次，重启不丢）。
2. 或者用管理员 PowerShell 手动执行上面那条 netsh（HTTP 与 HTTPS 现在共用 4173 一个端口，放行这一个就够）。
3. 手机与电脑必须同一 Wi-Fi、同一网段（手机 Wi-Fi 详情看 IP 是否 192.168.3.x 开头，不能一个是 5G 一个是 4G/访客网络）。
4. 先用手机打开 `http://<电脑IP>:4173/ping`：能看到 `VELOLAB PING OK` 说明端口通了；再打开 `https://<电脑IP>:4173/phone.html?code=XXXX`。
5. HTTPS 页会出现证书警告（自签证书），点「高级 → 继续访问」；不点继续，页面拿不到摄像头权限。
6. 仍不行就用「视频」模式：手机录 10 秒侧拍，传回电脑分析。

## 六、拍摄与标定要点

- 相机与车严格侧面垂直，镜头与车同高，全身（含脚踏最低点）入镜，光线均匀、背景干净。
- 照片模式请**在下死点（脚踩到最低点）按快门**，膝角才与 25–35° 的目标区间可比。
- 视频采样 6–10 秒、保持正常踏频；KOPS（膝前移）需要像素标定，程序用「踝部竖直行程 ÷ (2×曲柄长)」自动标定。

## 八、已知限制

- 角度误差约 ±2–3°（正侧面、整车入镜、光线均匀时最好；相机偏 10° 就会有几度系统偏差），单次调整不要超过 10mm，改完重测。
- 照片模式给不出踏频、左右不对称、上死点姿态。
